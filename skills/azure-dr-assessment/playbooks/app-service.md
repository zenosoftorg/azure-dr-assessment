# Azure App Service

## Mechanisms

### Zone redundancy
- Replicates: the plan's VM instances across availability zones of one region; state in the app's file system is stored in zone-redundant storage and synchronously replicated between zones. It protects against a zone failure, not a region failure.
- Paired: no
- Nonpaired: no
- Failover: Microsoft-managed
- Estimated RPO: unknown (Learn says file-system state is synchronously replicated between zones but publishes no RPO figure; the mechanism does not cover a region outage)
- Estimated RTO: unknown (Learn: the platform detects the failure and initiates a response with no manual step, but it attempts to find replacement instances on a best-effort basis and publishes no recovery time)
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-app-service

### Automatic backups
- Replicates: app content and, optionally on restore, app configuration, taken hourly by the platform without configuration, kept 30 days, stored in the same datacenter as the app
- Paired: no
- Nonpaired: no
- Failover: not applicable
- Estimated RPO: unknown (Learn: hourly and not configurable, but the backups are stored in the same datacenter as the App Service and Learn does not recommend relying on them as a DR plan, so they do not bound the loss in a region outage)
- Estimated RTO: unknown (Learn publishes no restore time; the backups are not a regional DR path)
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### Custom backups
- Replicates: the web app's files and configuration, backed up on a schedule to an Azure Storage account that you configure (Learn: use custom backups, not automatic backups), then copied to a storage account the DR region can read; a new app in a second region is restored from the copy
- Paired: yes
- Nonpaired: yes
- Failover: manual
- Estimated RPO: 2h (the planning figure from the multi-region article, "as frequently as every two hours", which is also why backup-restore uses it; Learn's pages differ on the shortest schedule, see the constraint on that; the real value adds the time to copy the backup files to the DR region, for which Learn gives no figure; TC-6 measures it)
- Estimated RTO: unknown (Learn: for a passive-cold design the RTO "could be hours or even days" because you detect the outage and create and restore the app yourself; no figure is published)
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service

## Constraints

### App Service is a single-region service
Learn: "App Service is a single-region service. If the region becomes unavailable, your application is also unavailable." It lists what you do to reduce that risk: deploy your application to plans in each region, configure load balancing and failover policies, and replicate your data across regions so that you can recover your last application state. Learn names no built-in cross-region replication and no Microsoft-managed regional failover for App Service.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-app-service#resilience-to-region-wide-failures

### No page read requires the DR region to be the primary's pair
Learn's multi-region tutorial says "Review the available region pairs and select two paired regions for your web apps" and tests "the apps in the paired regions", but this is the tutorial's example and it is not stated as a technical rule. This means (inference from the pages read for this playbook, none of whose constraints below states a pair condition for the second app; the only pair split is the copy of backup files, see the constraint on backup replication) that a DR region that is not the pair is a valid target for secondary-app, subject to the tier and feature checks in the constraints below.
- Source: https://learn.microsoft.com/en-us/azure/app-service/tutorial-multi-region-app

### A Functions app is a sites resource and its plan is a serverfarms resource
Learn's infrastructure-as-code article for Functions deploys a function app as a Microsoft.Web/sites resource whose kind contains functionapp (for example "functionapp,linux"), and "All Functions hosting plans use a Microsoft.Web/serverfarms resource type". A function app is therefore in the scope of this playbook through the same two ARM types, and the constraints on Functions below apply to the sites whose kind contains functionapp.
- Source: https://learn.microsoft.com/en-us/azure/azure-functions/functions-infrastructure-as-code

### Three multiple-region approaches with different recovery characteristics
Learn describes active-active, active-passive and passive-cold architectures. Its comparison gives a recovery time of real-time or seconds, minutes and hours, and a recovery point of real-time or seconds, minutes and hours, with high, medium and low cost, for the three in that order. Active-active and active-passive deploy code with CI/CD pipelines (preferred); passive-cold uses backup and restore and needs new App Service resources during the downtime. Active-passive is the model that the option secondary-app builds and passive-cold is the model of backup-restore; an active-active deployment is the same build with both Front Door origins at priority 1.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service#recovery-objectives-and-approach-comparison

### A plan holds compute in one region, so DR needs a plan in the DR region
Learn: when you create an App Service plan in a region, you create a set of compute resources for that plan in that region, and the apps in the plan run on them. A plan defines operating system, region, number of VM instances, VM size and pricing tier. Learn lists "the app needs resources in a different geographical region" as a reason to use a new plan. So the DR region needs its own plan and its own app, and nothing moves between regions by changing a setting on the existing plan.
- Source: https://learn.microsoft.com/en-us/azure/app-service/overview-hosting-plans

### Available pricing tiers depend on operating system and region
Learn: "The pricing tiers available to your App Service plan depend on the operating system, region, and other factors." Each tier provides a subset of features, including custom domains and TLS/SSL certificates, autoscaling, deployment slots, backups and Traffic Manager integration. This is a per-region availability check, not a pair rule: whether the DR region offers the tier the workload needs is decided by looking at that region.
- Source: https://learn.microsoft.com/en-us/azure/app-service/overview-hosting-plans#pricing-tiers

### Zone redundancy needs Premium v2 to v4, two instances and a supporting scale unit
A zone-redundant plan needs a Premium v2 to v4 plan type, at least two instances, a region that supports availability zones (for Premium v4, a region that supports v4 plans), and a scale unit that supports zone redundancy; you do not directly control the scale unit, and a plan on a scale unit without support cannot be made zone redundant (Learn's answer is to redeploy the apps to a new plan on a different scale unit). A DR plan that should be zone redundant has to be checked in the DR region for these conditions.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-app-service#requirements

### Scale-out, autoscale and slot limits depend on the tier
Learn's App Service limits list the maximum instances per tier (3 dedicated for Basic, 10 for Standard, 30 for Premium v2 to v4 and 100 for Isolated), autoscale from Standard upward, and staging slots from Standard upward (5 for Standard, 20 for Premium and Isolated). A DR plan in a lower tier than the primary has lower limits, so the primary's instance count may not be reachable in the DR plan.
- Source: https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits#azure-app-service-limits

### Active-passive: Front Door routes by health probe and autoscale fills the standby
In the active-passive architecture Azure Front Door routes traffic to one region at a time. On a region failure its health probes detect the faulty origin and route traffic to the secondary region, and the network load triggers preconfigured autoscale rules that scale out the secondary web app. On failback Azure Front Door automatically directs traffic back to the primary region. Learn says that during a geo-failover the recovery time "depends in part on the time required to scale out instances" (or to scale up and scale out, for the smaller secondary plans below). Learn states the dependence on health-probe detection, with a default probe of every 30 seconds, for the active-active architecture; for active-passive it is an inference that Front Door's probes decide when the switch happens, because the same Front Door mechanism does the routing.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service#active-passive-architecture

### Front Door health probes default to every 30 seconds
Learn's Front Door health probe article gives a default probe frequency of 30 seconds, and says that a 200 OK status code indicates a healthy origin and any other status code or no valid response is a probe failure. Front Door looks at the last n responses (SampleSize) and the origin is healthy if at least x (SuccessfulSamplesRequired) are healthy; if probes fail for every origin of a group, Front Door treats all origins as unhealthy and routes round robin across all of them.
- Source: https://learn.microsoft.com/en-us/azure/frontdoor/health-probes

### The secondary plan can be smaller, with a ranking of how much
To reduce cost Learn ranks three secondary plans: preferred, same pricing tier as the primary with the same or fewer instances (keeps feature and VM-size parity); less preferred, same tier family with a smaller VM size and fewer instances (you might need to scale up manually when the secondary becomes active); least preferred, a different pricing tier with fewer instances (check that the plan has the features the app needs; differences in feature availability can delay recovery). If the secondary is not set to run as the active region you might need to adjust the pricing tier manually, because autoscaling requires Standard tier or higher.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service#active-passive-architecture

### Both apps must accept traffic only from the same Front Door
Learn's tutorial restricts both the primary and the standby app with an access restriction that uses the AzureFrontDoor.Backend service tag plus the x-azure-fdid header set to the profile's Front Door ID, so that traffic cannot bypass the Front Door web application firewall and DDoS protection. The restriction is a setting of each app, so the DR app needs its own rule. The profile ID is the identity of one Front Door instance, so (inference) a recreated profile needs the rule on both apps to be updated.
- Source: https://learn.microsoft.com/en-us/azure/app-service/tutorial-multi-region-app#restrict-access-through-azure-front-door-only

### Keep both regions in sync with infrastructure as code and CI/CD
Learn: manage each region's resources with infrastructure as code (Bicep or Terraform) so that the configuration stays in sync even when the affected region cannot be reconciled by hand, and deploy the same build to every region by CI/CD. To meet a recovery point of zero for application content, use a CI/CD solution to deploy application files to both web apps. Store application state outside the App Service file system, for example in a database or Azure Storage, and configure those components for geo-redundancy.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service

### File-system state is reduced by writing to a geo-redundant mounted share, which Learn ties to a paired region
Learn's tip: if the app modifies the file system and the app's region has a paired region, write to a mounted Azure Storage share instead of the web app's /home content share, with GZRS or GRS for the share; replication is asynchronous, so include the possible lag and the storage-account failover in the recovery design. The tip is stated for a region with a pair. This means (inference) that GZRS or GRS on the share reaches the pair and not a DR region that is not the pair; for such a DR region the state has to be kept in a store that replicates to that region (see the playbook of the storage service), or the app has to be changed so that it does not write state to disk.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service#recommendations

### Backups are limited by tier, size, frequency and retention
Back up and restore is supported in the Basic, Standard, Premium and Isolated tiers; Basic can back up and restore only the production slot. Automatic backups: 30 GB, hourly, retained 30 days, not configurable, not downloadable, no partial backups, not over a virtual network, no linked database. Custom backups: 10 GB of which 4 GB can be a linked database, frequency configurable "every 2 hours minimum, up to 12 backups per day (manual + scheduled)", retention 0 to 30 days or indefinite, downloadable as Azure Storage blobs, partial backups and backups over a virtual network supported, and a storage account is required.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup#automatic-vs-custom-backups

### Two Learn pages disagree on the custom backup frequency; the stricter one is used
The App Service limits page lists "Scheduled backups every hour, a maximum of 50 backups per day" for Premium and Isolated, while the backup article states, for all tiers, every 2 hours at minimum and up to 12 backups per day. This playbook plans with the figure of the backup article (2 hours, 12 per day), which is also the multi-region article's "as frequently as every two hours", and writes the Estimated RPO of the custom backups as 2h without calling it a Learn minimum. A team that wants an hourly schedule has to check the portal and the backup article before it plans for it.
- Source: https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits#azure-app-service-limits

### Custom backups need a storage account with SAS authorization
A custom backup needs an Azure Storage account in the same subscription (select an existing one or create one) and a container. Learn: custom backups need an account "that supports Shared Access Signature (SAS)-based authorization", and "Managed Identity-based authentication to the storage account isn't supported for App Service backup and restore operations". In the storage account each backup is a ZIP file with the backup data and an XML file with a manifest of its contents. Altering any of the files in the websitebackups container "can cause the backup to become invalid and nonrestorable".
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### A firewall-protected backup storage account needs virtual network integration
Custom backups can go to a firewall-protected storage account if the app is integrated with a virtual network (or is in an App Service Environment v3) and the storage account allows access from that network. After the setting is saved, every manual backup, scheduled backup and restore goes through the virtual network, and a change to the app, the network or the storage account that blocks the access makes the backup or restore fail. A backup over a virtual network cannot include a linked database.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup#back-up-and-restore-over-azure-virtual-network

### A backup holds content only for part of an app
In an automatic or custom backup the restored content is the app content under %HOME% (Windows), /home (Linux) or the persistent storage of custom containers. Not restored: the content of a run-from-ZIP package and content from any custom-mounted Azure storage, such as an Azure Files share. Each backup is a complete offline copy, not an incremental one.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### Many settings are not restored from a backup
Restore of app configuration brings back native log settings, Application Insights configuration and health check. It does not restore: network features (private endpoints, hybrid connections, virtual network integration), authentication, managed identities, custom domains, TLS/SSL, scale out, diagnostics with Azure Monitor, alerts and metrics, the backup configuration itself, associated deployment slots and a linked database. For a custom backup the XML manifest lists the custom domains, and when the backup is restored the domains are added to the destination app if there is no DNS conflict, and the destination app's other custom domains are removed. Everything on the not-restored list is rebuilt from infrastructure as code in the DR app. Neither of Learn's two tables lists app settings or the runtime stack, so the playbook does not rely on a backup for them either.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### A restore stops the target and overwrites an existing slot
Learn: App Service stops the target app or target slot while restoring a backup, and to minimise downtime for a production app you restore to a deployment slot first and then swap it into production. Restoring into an existing slot erases and overwrites all existing data in its file system. Restoring without a _backup.filter file deletes all existing files in the app and replaces them with the files in the backup. A failover restore therefore targets a new, empty DR app, never the primary app.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### Restore to another region of the same subscription is supported, to another subscription needs a copy
Learn: an app can be restored to a different region within the same subscription by the same steps as a normal restore; the backup storage of the source app must be reachable by the target app, and the portal lets you select an app in another region as long as it is in the same subscription. For a different subscription, make a custom backup, download the ZIP and XML, upload both to the target storage account, and restore with Storage as the source. Learn also says "Backups can be restored to a target app of the same OS platform as the source app" (in its App Service Environment section); this means (inference) that the DR app uses the OS of the source app.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### Automatic backups are not a DR plan
Learn: automatic backups are stored in the same datacenter as the App Service, "We don't recommend that you rely on automatic backups as your disaster recovery plan", and "You can't stop automatic backups". The Backups page of an app lists its automatic and custom backups and their status.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### Most solutions should not rely only on backups
Learn's reliability article: backups help when it is difficult to redeploy code or when you store state on disk, "Most solutions shouldn't rely exclusively on backups", and backups protect against some risks that the other capabilities do not. This is why backup-restore is ranked after secondary-app.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-app-service#backup-and-restore

### Linked database backups end on 31 March 2028
Learn: starting 31 March 2028 App Service custom backups no longer back up linked databases, and the option has been removed from new custom backups in stages (linked MySQL and PostgreSQL in November 2025, Azure SQL and SQL Server in April 2026). Flexible Server for MySQL and PostgreSQL is not supported in custom backups, and Learn recommends the native backup and restore tools of each database service. The data of the app is therefore recovered through the playbook of its data service and not through the app backup.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup

### Functions apps with Azure Files content storage have no automatic backups
Learn: automatic backups are supported for Azure Functions when the app does not use Azure Files content storage (WEBSITE_CONTENTAZUREFILECONNECTIONSTRING not configured). Function apps on the Consumption and Elastic Premium plans typically use Azure Files and so do not support automatic backups; Basic, Standard and Premium plans may also be configured with Azure Files content storage, with the same result. Learn's FAQ states this for automatic backups only; the pages read do not say whether custom backups of such an app work, so treat that as unknown and prove it with TC-7 before relying on backup-restore for a function app.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-backup#does-azure-functions-support-automatic-backups

### Functions multiregion: active-active for HTTP triggers, active-passive for non-HTTP triggers
Learn: "Functions is a single-region service. If the region becomes unavailable, your Functions resource is also unavailable." You are responsible for deploying function apps to multiple regions, managing traffic between regions, implementing failover, ensuring data consistency and monitoring. For HTTP-triggered functions use an active-active pattern with Azure Front Door, which removes an unhealthy endpoint from rotation. For non-HTTP triggers (Service Bus, Event Hubs) use active-passive, in which the function instances in the secondary region remain idle because they do not receive messages, so that only one function processes each message; Learn's example drives the failover from the event source: when the Event Hubs alias is switched to the secondary namespace, "The secondary function app becomes active and triggers automatically", and each function app's trigger uses the direct connection string of its own namespace. Learn describes no step that stops or starts the secondary function app. For durable functions Learn points to its own disaster recovery and geo-distribution article.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-functions

### Backup files cross regions by storage replication that depends on the pair
For passive-cold, Learn splits by pair. In a region with a pair: a Standard storage account in the app's region with RA-GZRS (or RA-GRS if RA-GZRS is not available), which copies data asynchronously to the secondary region and gives read-only access there so that backups can be retrieved when the primary region is unavailable; monitor Last Sync Time; for a recovery point of 15 minutes or less for block blobs consider Geo Priority Replication. In a region without a pair: a second Standard storage account in another region with locally redundant storage that receives the backups by Azure Storage object replication, or by AzCopy when you need control over the frequency; object replication does not guarantee replication speed, but the replication status of a blob can be checked. This means (inference) that for a DR region that is not the primary's pair the object replication or AzCopy path is the one that reaches it, because RA-GRS and RA-GZRS copy to the secondary region of the storage account, which Learn's pair split ties to the region's pair.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service

### Object replication needs versioning and a change feed, and skips some blobs
Object replication asynchronously copies block blobs between a source and a destination account. It needs the change feed on the source account and blob versioning on both accounts, and the source and destination accounts "aren't immediately in sync". Learn describes the check on the source account ("You can check the replication status for a blob in the source account"); this means (inference) that in an outage of the source region the status cannot be read from the DR account. When the status of a blob shows failure, causes include a destination container that is gone, a blob encrypted with a customer-provided key on write, blobs in the archive tier and a destination container or blob under an immutability policy. Learn gives a figure of 99.0% of objects within 15 minutes (SLA-backed) only for object replication priority replication, when source and destination are in the same continent, for supported workloads; without it Learn gives no replication time.
- Source: https://learn.microsoft.com/en-us/azure/storage/blobs/object-replication-overview

### In passive-cold you detect the outage and the recovery takes hours or more
Learn: if the primary region is unavailable you are responsible for detecting the outage, and you deploy the App Service resources and dependent resources in the secondary region by using the backups from the secondary region's storage account. The recovery time "could be hours or even days", the recovery point depends on the backup frequency and the time to replicate backups between regions, and after the restore you may need to address dependencies such as DNS records and TLS certificates. Passive-cold often relies on manual intervention and Learn recommends active-active or active-passive for most production-grade solutions.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service#passive-cold-architecture

### A custom domain can be bound to a second app before the name points at it
Learn's migration of an active DNS name binds the name to an App Service app ahead of the switch, without downtime: a TXT record `asuid.<subdomain>` (`asuid` for a root domain) with the app's Custom Domain Verification ID verifies the ownership, the domain is then added to the app (validation passes with the TXT record alone), and the record that serves traffic is remapped later, to the app's default host name for a CNAME or to its IP address for an A record. The app must not be in the Free tier. A domain name can be assigned to only one app in each deployment unit, so two apps that hold the same name must be in different deployment units; apps in the same resource group and region share one, Learn gives no guarantee that another resource group or region gives another one, and the deployment unit shows in the app's FTP/S host name `<deployment-unit>.ftp.azurewebsites.windows.net`.
- Source: https://learn.microsoft.com/en-us/azure/app-service/manage-custom-dns-migrate-domain

### A free managed certificate needs the name mapped to the app; a company certificate can be bound ahead
Learn: a free App Service managed certificate needs the domain mapped to the app (for a subdomain, a CNAME directly to `<app-name>.azurewebsites.net`), does not support private DNS and is not exportable; for a migrated live domain it can be added only after the name is remapped. A private certificate (imported from Key Vault, an App Service certificate, or an uploaded PFX) must hold the whole chain, have the server authentication extended key usage and be signed by a trusted certificate authority; App Service (multitenant) does not accept a private CA certificate for inbound TLS. A private certificate is stored per resource group, region and OS combination (the webspace), so an app in another region imports it again. Importing from Key Vault needs the Key Vault Certificate User role (or the access policy) for the App Service resource provider on the vault, and a renewed Key Vault certificate is synced to App Service within 24 hours.
- Source: https://learn.microsoft.com/en-us/azure/app-service/configure-ssl-certificate

### Resolvers cache a DNS record until its TTL expires
Learn: a DNS server caches the resource records it resolves and can answer from its cache as long as the record's Time-To-Live (TTL) has not expired. After the record of the app's name is changed, clients can therefore still get the old answer for up to the TTL, so the TTL counts toward the recovery time of a switch made by a DNS record change.
- Source: https://learn.microsoft.com/en-us/windows-server/networking/dns/queries-lookups

### Built-in roles for the app and the plan
Learn's built-in roles: Website Contributor manages websites but not web plans, and Web Plan Contributor manages the web plans for websites; neither allows you to assign roles in Azure RBAC. Build assigns them to the roles that the Failover and Failback tables name.
- Source: https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/web-and-mobile#website-contributor

### Built-in roles for Front Door and DNS
Learn's built-in roles: CDN Profile Contributor manages CDN and Azure Front Door Standard and Premium profiles and their endpoints but cannot grant access to other users, and DNS Zone Contributor manages DNS zones and record sets in Azure DNS without controlling who has access to them.
- Source: https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/networking#cdn-profile-contributor

### Built-in roles for the backup storage
Learn's built-in roles: Storage Blob Data Contributor reads, writes and deletes Azure Storage containers and blobs, and Storage Blob Data Reader reads and lists them. App Service itself reaches the backup storage with SAS, so these roles are for the people and jobs that inspect or copy backup files.
- Source: https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/storage#storage-blob-data-contributor

### A role that assigns roles is needed for the app's identity
Learn's Role Based Access Control Administrator manages access to Azure resources by assigning roles using Azure RBAC (it includes the control plane read action for all resources). Website Contributor and Web Plan Contributor cannot do this (see the constraint on the built-in roles for the app and the plan). The managed identity of the DR app needs role assignments on the DR data services, so a role holder with Role Based Access Control Administrator at the scope of those resources makes them; Build assigns it to a named role, the access administrator.
- Source: https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/privileged#role-based-access-control-administrator

## Non-paired options

### secondary-app: Second app and plan in the DR region behind Front Door
- Kind: workaround
- Target: dr-region
- Uses mechanism: none
- Estimated RPO: 0 (Learn: "To meet an RPO of zero for application content, use a CI/CD solution to deploy application files to both web apps"; this covers application content only, so the Estimated RPO of the data tier governs everything else: application state outside the file system follows the Estimated RPO of the data service that holds it, set by that service's playbook; TC-1 proves the content is the same build on both apps and TC-5 checks that nothing the app needs lives only on one app's disk)
- Estimated RTO: 15m (Estimated, team-set starting value: the switch-over target the team sets for the active-passive design; Learn gives minutes for active-passive and says the time depends in part on the time to scale out instances; the dependence on Front Door's probe detection (default every 30 seconds) is Learn's text for active-active and an inference here; TC-3 proves it)
- Prerequisites: a DR plan in a region where the plan's tier is available for the plan's OS (see the constraint on tiers), on Learn's preferred footing of the same tier as the primary with the same or fewer instances (zone redundancy only where the constraint on zone redundancy is met); the same OS, runtime stack and container image source as the primary; a Front Door profile with an origin group, a health probe path on each app that returns the status Front Door counts as healthy (see the constraint on health probes), the primary origin at priority 1, the DR origin at priority 2 and a route; network access to both apps restricted to that Front Door instance (see the constraint on Front Door-only access), with an extra rule for the test source of TC-2; a pipeline that deploys the same build to both apps; autoscale on the DR plan (Standard or higher) like the primary's; a custom domain and DNS pointing at Front Door and not at one app (the Learn pages read for this playbook do not describe custom domains or certificates on Front Door, so follow the Front Door documentation for that part); roles from the secondary-app Build step that grants the roles the Failover and Failback tables use; data services replicated to the DR region by their own playbooks, with the DR app pointing at the DR endpoints.
- Cost notes: the DR plan bills per instance while it runs, so a standby plan with instances costs even without traffic (Learn lets you reduce this by fewer instances and a lower tier, at the cost of parity and recovery time); Front Door; a second set of dependent resources; cross-region data transfer; extra pipeline runs; no price.
- Gives up: no built-in replication, so the file system of the primary app is not copied and state on disk is lost unless the app is changed; Learn's design relies on scale-out at failover and the Estimated RTO depends on it (inference: DR capacity is not reserved, so a lower tier or fewer instances lengthens recovery); two deployments to keep in sync, with drift as the main risk; non-HTTP-trigger functions need the event source's own failover to activate the DR app; a dependency on Front Door routing for the switch.
- Recommended when: the app is stateless or keeps its state in data services that replicate to the DR region, a recovery time of minutes is needed, and the primary's tier is available in the DR region; a good first choice for a DR region that is not the primary's pair (inference: Learn states no pair condition for it, see the constraint on pairs).
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service
- Decides slots: traffic-dns

### secondary-app-dns: Second app and plan in the DR region behind the company's DNS
- Kind: workaround
- Target: dr-region
- Uses mechanism: none
- Estimated RPO: 0 (Learn: "To meet an RPO of zero for application content, use a CI/CD solution to deploy application files to both web apps", see the constraint on keeping both regions in sync; as for a second app behind Front Door this covers application content only, and application state outside the file system follows the Estimated RPO of the data service that holds it, set by that service's playbook; TC-1 proves the content is the same build on both apps and TC-5 checks that nothing the app needs lives only on one app's disk)
- Estimated RTO: 30m (Estimated, team-set starting value: the switch-over target the team sets from the failover decision to the first request answered by the DR app: the change of the record in the company's DNS, the TTL of that record, which counts toward the RTO because resolvers can answer from their cache until it expires (see the constraint on TTL), and the scale-out of the DR plan; Learn publishes no figure for this design; TC-10 proves it)
- Prerequisites: a DR plan in a region where the plan's tier is available for the plan's OS (see the constraint on tiers), on Learn's preferred footing of the same tier as the primary with the same or fewer instances; the same OS, runtime stack and container image source as the primary; the app's custom domain bound to the DR app ahead of the switch by its domain verification TXT record, and a TLS certificate for that name that the company owns (from Key Vault or an App Service certificate, signed by a trusted certificate authority) bound on both apps, because a free managed certificate needs the name mapped to the app (see the constraints on binding a custom domain ahead and on certificates); the record of the app's name in the company's DNS, its type, its TTL and the role that changes it, which the company's DNS rules supply; the DR app's entry point that the record will point at; a pipeline that deploys the same build to both apps; autoscale on the DR plan (Standard or higher) like the primary's; roles from the secondary-app-dns Build step that grants the roles the Failover and Failback tables use; data services replicated to the DR region by their own playbooks, with the DR app pointing at the DR endpoints.
- Cost notes: the DR plan bills per instance while it runs, so a standby plan with instances costs even without traffic; the certificate; a second set of dependent resources; cross-region data transfer; extra pipeline runs; no Front Door; no price.
- Gives up: no built-in replication, so the file system of the primary app is not copied; the switch is manual (no health probe moves traffic) and waits for the team that changes the record, and clients follow it only when their cached answer expires, so the TTL is part of every failover and failback; DR capacity is not reserved and the Estimated RTO depends on the scale-out (inference, as for a second app behind Front Door); two deployments and two certificate bindings to keep in sync.
- Recommended when: the company's own DNS is authoritative for the app's name and an Azure-side router such as Front Door or Traffic Manager is not used (a company pattern that decides the traffic-dns slot vetoes secondary-app); otherwise as secondary-app.

### backup-restore: Restore a custom backup into a new app in the DR region
- Kind: backup-restore
- Target: dr-region
- Uses mechanism: Custom backups
- Estimated RPO: 2h (the planning figure from the multi-region article, "as frequently as every two hours"; Learn's pages differ on the shortest schedule, see the constraint on that; add the time that the backup files need to reach the DR region by object replication or AzCopy, which Learn does not give; TC-6 measures the real value)
- Estimated RTO: 24h (Estimated, team-set starting value: Learn says the passive-cold RTO "could be hours or even days", because the team detects the outage, creates the plan and app, restores and fixes DNS and TLS; TC-7 proves it in the first drill and the measured time becomes Demonstrated)
- Prerequisites: App Service in a tier that supports backups and content within the custom backup size limit, with large or static content excluded (see the constraints on backup limits and on what a backup holds); custom backups on a schedule (not shorter than 2 hours, see the constraint on the conflict between pages) to a Standard storage account in the app's region, configured as the constraints on SAS and on virtual network backup require; a second Standard, locally redundant storage account in the DR region that receives the backup container by object replication, or by an AzCopy job when the team wants to set the frequency (see the constraint on object replication for its prerequisites); a read-access geo-redundant copy (RA-GRS or RA-GZRS) of the first account stays a second copy in the pair and is not the DR region copy; the DR region offers the plan's tier for the plan's OS; roles from the backup-restore Build step that grants the roles the Failover and Failback tables use.
- Cost notes: the two storage accounts and their transactions, versioning and change feed, the object replication or AzCopy transfers, the retained backups; the DR plan exists only during a drill or a failover, so its compute cost starts when it is created; no price.
- Gives up: a recovery time of hours or longer, with manual detection and a manual rebuild; the data written after the last backup that reached the DR region; every setting on the not-restored list, which has to come from infrastructure as code; run-from-ZIP content, mounted storage content and the linked database, which have their own DR paths; custom backups are limited in size (see the constraint on backup limits); Functions apps with Azure Files content storage (automatic backups are not supported for them and the pages read do not say whether custom backups are).
- Recommended when: the app is low priority or cheap to rebuild, a recovery time of hours is acceptable, its content is within the backup size limit and the cost of a running second plan is not wanted; also as the second copy of the content next to secondary-app.
- Source: https://learn.microsoft.com/en-us/azure/architecture/web-apps/guides/multi-region-app-service/multi-region-app-service

## Migration from a paired setup

### Recognise today's setup
App Service has no built-in replication, so a paired DR does not show as a setting of the app or the plan: the inventory shows a primary plan and its apps, and nothing for the DR unless the team built it. Two built setups are visible. First, a second plan and app (microsoft.web/serverfarms and microsoft.web/sites) in the primary's pair region, with a Front Door profile or Traffic Manager profile whose origins or endpoints point at both apps; record it as secondary-app in the pair only from the origin or endpoint settings, never from names or co-location. Second, a custom backup configuration on the app (storage account and schedule) whose storage account has a read-access geo-redundant SKU (RA-GRS or RA-GZRS, the SKUs Learn names for retrieving backups from the secondary region, which is the pair): record it as backup-restore in the pair; a storage account with GRS or GZRS (no read access) is not named by Learn for backups, so record it as Unknown. Automatic backups do not show as a resource setting in an inventory, although the Backups page of the app lists them, and they are not a DR plan; a Functions app (kind contains functionapp) on the Consumption or Elastic Premium plan is a different case (no automatic backups with Azure Files content storage). The plan shows its tier, its instance count and whether it is zone redundant. The inventory cannot show whether the backups succeed or are recent, whether the DR app is current, what is outside the backup, or whether the Front Door priorities and access restrictions are as intended; those are the Validate steps. Where nothing is found, record Unknown for today's DR. Migration to a DR region that is not the pair is decided per app by option id: secondary-app builds a second plan and app in the DR region behind Front Door, secondary-app-dns builds one behind the company's DNS, and backup-restore builds a second backup copy in the DR region; a second app and a backup copy can exist for one app.

### Build
1. secondary-app: check the DR region for the plan's tier and OS (the available tiers depend on operating system and region) with the portal or the CLI list of locations for the SKU, check the limits of the tier against the primary's instance count (Learn's App Service limits list the maximum instances per tier), and check the zone redundancy requirements if the primary plan is zone redundant (Premium v2 to v4, two instances, supporting scale unit); record the result as the DR plan design (tier, instances, zone redundancy, autoscale limits) with the preferred footing of the same tier.
2. secondary-app: grant the roles that the Failover and Failback tables use: to the platform engineer role, Website Contributor and Web Plan Contributor on the DR resource group and on the primary's resource group (Failback restores into the primary app); to the network engineer role, CDN Profile Contributor on the Front Door profile and DNS Zone Contributor on the DNS zone if DNS is changed; to the application engineer role, Website Contributor on the DR apps; to the access administrator role, Role Based Access Control Administrator on the DR resource group and on the resource group of each DR data service (the subscription's owner role assigns it; it is the only role in this playbook that creates role assignments); to the pipeline identity, Website Contributor on both apps.
3. secondary-app: deploy the DR plan and the DR app from the same infrastructure-as-code template as the primary, with region parameters, so that the runtime stack, app settings (with DR endpoints), virtual network integration, private endpoints, managed identity, custom domains, TLS bindings, diagnostic settings, alerts, health check and autoscale rules exist in the DR app (Learn's backup tables restore only log settings, Application Insights and health check, and none of the others).
4. secondary-app: the access administrator role assigns the DR app's managed identity its roles on the DR data services, vault and registry (the role names come from the playbooks of those services; Website Contributor cannot assign roles), and the platform engineer role sets the app settings so that the DR app reads the DR endpoints.
5. secondary-app: set up traffic: add the DR app as an origin at priority 2 in the Front Door origin group (the primary stays at priority 1), set the health probe path, interval, sample size and successful-samples-required that the team chooses (the tutorial example uses 60 seconds, 4 samples and 3 required; Learn's default probe interval is 30 seconds) and the route; add the access restriction with the AzureFrontDoor.Backend service tag and the x-azure-fdid header of the profile to both apps; point the custom domain and DNS at Front Door.
6. secondary-app: set up the pipeline so that every release deploys the same build to both apps (the DR app is not behind a manual step); add autoscale on the DR plan with the primary's rules so that it scales up to the primary's instance count when traffic arrives; set alerts and Application Insights availability tests for both regions so that the team is told of a regional outage (Learn: you detect it yourself).
7. secondary-app: for a function app with non-HTTP triggers deploy the DR function app and leave it idle, because in Learn's pattern it receives no messages until the event source fails over, each app's trigger uses the direct connection string of its own namespace, and the failover of the event source (for example the Event Hubs alias) activates the DR app, which "triggers automatically"; Learn describes no step that stops or starts the app, so none is added here. For HTTP triggers use the same Front Door origin group.
8. secondary-app-dns: check the DR region for the plan's tier and OS (the available tiers depend on operating system and region) with the portal or the CLI list of locations for the SKU, check the limits of the tier against the primary's instance count, and check the zone redundancy requirements if the primary plan is zone redundant (Premium v2 to v4, two instances, supporting scale unit); record the result as the DR plan design (tier, instances, zone redundancy, autoscale limits) with the preferred footing of the same tier.
9. secondary-app-dns: grant the roles that the Failover and Failback tables use: to the platform engineer role, Website Contributor (it manages sites and their certificates) and Web Plan Contributor on the DR resource group and on the primary's resource group (Failback deploys into the primary app); to the access administrator role, Role Based Access Control Administrator on the DR resource group and on the resource group of each DR data service (the subscription's owner role assigns it); to the pipeline identity, Website Contributor on both apps; on the key vault that holds the certificate, the Key Vault Certificate User role for the App Service resource provider, assigned by a holder of Role Based Access Control Administrator on that vault (Website Contributor cannot assign roles); the record in the company's DNS is changed by the role that the company's DNS rules name, not by an Azure role.
10. secondary-app-dns: deploy the DR plan and the DR app from the same infrastructure-as-code template as the primary, with region parameters, so that the runtime stack, app settings (with DR endpoints), virtual network integration, private endpoints, managed identity, access restrictions for the same client networks as the primary's, diagnostic settings, alerts, health check and autoscale rules exist in the DR app (Learn's backup tables restore only log settings, Application Insights and health check, and none of the others); check that the DR app's deployment unit (the host name of its FTP/S URL) differs from the primary's, because only one app in each deployment unit can hold the custom domain and Learn does not guarantee another unit for another region (see the constraint on binding a custom domain ahead); if it is the same, create the DR plan again in another resource group until it differs.
11. secondary-app-dns: the access administrator role assigns the DR app's managed identity its roles on the DR data services, vault and registry (the role names come from the playbooks of those services), and the platform engineer role sets the app settings so that the DR app reads the DR endpoints.
12. secondary-app-dns: bind the custom domain to the DR app ahead of the switch: copy the DR app's Custom Domain Verification ID, have the record owner role add the TXT record `asuid.<subdomain>` (`asuid` for a root domain) with that ID in the company's DNS, then add the custom domain to the DR app (the validation passes with the TXT record alone); do not touch the record that serves traffic, which keeps pointing at the primary.
13. secondary-app-dns: import the company's certificate for the name into the DR app (from Key Vault, which syncs a renewed certificate within 24 hours, or as an App Service certificate or an uploaded PFX with the whole chain) and create the TLS binding of the custom domain on the DR app; the certificate is stored per resource group, region and OS, so the DR app imports its own copy, and the primary keeps its binding. A free managed certificate cannot be issued to the DR app while the name points at the primary.
14. secondary-app-dns: write the traffic switch into the runbook from the company's DNS rules: the record of the app's name (type and name), its value today (the primary's entry point), its DR value (the DR app's default host name `<app-name>.azurewebsites.net` for a CNAME, the DR app's IP address for an A record, or the address of the DR app's private endpoint when clients reach the app privately, see the playbook of private endpoints and DNS), its TTL, which counts toward the Estimated RTO, and the role that changes it; write "not supplied by the application team" for a value the team has not supplied.
15. secondary-app-dns: set up the pipeline so that every release deploys the same build to both apps; add autoscale on the DR plan with the primary's rules; set alerts and Application Insights availability tests for both regions so that the team is told of a regional outage (Learn: you detect it yourself); a standard availability test resolves the name in public DNS and fails if it cannot, so the DR app's test calls its default host name, and the custom domain and certificate of the DR app are checked by the TC-9 test client, which resolves the name to the DR entry point.
16. secondary-app-dns: for a function app with non-HTTP triggers deploy the DR function app and leave it idle, as in Learn's pattern: it receives no messages until the event source fails over, each app's trigger uses the direct connection string of its own namespace, and the failover of the event source activates the DR app; for HTTP triggers the record in the company's DNS switches the function app like a web app (inference: Learn's pattern for HTTP triggers is active-active behind Front Door, and this option replaces Front Door with the company's DNS).
17. backup-restore: configure custom backups on each app: the storage account in the app's region and container (SAS-based; if the account has a firewall, enable backup over virtual network integration), a schedule not shorter than 2 hours, retention chosen by the team, and a _backup.filter file for content that should not be saved; record the backup size against the 10 GB limit.
18. backup-restore: create the second Standard storage account in the DR region (locally redundant), enable blob versioning on both accounts and the change feed on the source, and create the object replication rule for the backup container (or the AzCopy job on a schedule that the team sets, run from Azure Automation or another compute platform); enable replication metrics on the source account; for an app whose region has a pair with RA-GZRS or RA-GRS in place, keep that copy as a second copy.
19. backup-restore: write down what is outside the backup and give each item its DR path: run-from-ZIP package (redeploy from CI/CD), mounted storage (the storage playbook), linked database (the playbook of the data service), settings not restored (infrastructure as code), and for a Functions app with Azure Files content storage the redeploy from CI/CD.
20. backup-restore: grant the roles that the Failover and Failback tables use: to the platform engineer role, Storage Blob Data Contributor on the DR storage account, Storage Blob Data Reader on the primary one, and Website Contributor and Web Plan Contributor on the DR resource group and on the primary's resource group (Failback restores into the primary app); to the network engineer role, CDN Profile Contributor on the Front Door profile and DNS Zone Contributor on the DNS zone, whichever carries the traffic switch; to the access administrator role, Role Based Access Control Administrator on the DR resource group and on the resource group of each DR data service (as in the secondary-app Build step that grants the roles), which the failover step that rebuilds what a restore does not bring back uses for the identity of the restored app; these roles exist already after that secondary-app Build step when secondary-app is built.

### Validate
1. secondary-app: run TC-1 after every deployment, and weekly.
2. secondary-app: run TC-2 daily from the probe source that the extra access rule allows, and from outside it.
3. secondary-app: run TC-3 in a drill with the primary origin disabled: time the switch against the Estimated RTO and record the scale-out time; repeat at every DR drill and after every change to Front Door, the DR plan or the pipeline.
4. secondary-app: run TC-4 monthly, and after every change to network, identity or domains.
5. secondary-app: run TC-5 before cut-over, then at every release that changes how the app writes state.
6. secondary-app-dns: run TC-1 after every deployment, and weekly.
7. secondary-app-dns: run TC-9 daily from a test client that resolves the custom domain to the DR app's entry point, and monthly and after every change to network, identity, domains or certificates for the configuration part.
8. secondary-app-dns: run TC-10 in a drill with the primary treated as unreachable: time the failover decision, the record change in the company's DNS, the TTL wait and the first request answered by the DR app against the Estimated RTO, and record the scale-out time; repeat at every DR drill and after every change to the record, its TTL, the DR plan or the pipeline.
9. secondary-app-dns: run TC-5 before cut-over, then at every release that changes how the app writes state.
10. backup-restore: run TC-4 monthly, and after every change to network, identity or domains.
11. backup-restore: run TC-6 daily, and record the largest copy lag of the first week as the lag that TC-6 uses from then on.
12. backup-restore: run TC-7 in a restore drill into a new app in the DR region from the DR storage account only (the primary region's storage is treated as unreachable), at every DR drill and after every change to the backup configuration, the DR storage or the app's runtime stack.
13. backup-restore: run TC-8 monthly.
14. Record each result with its date; a time that a drill measured is Demonstrated, and everything else stays Estimated or Unknown.

### Cut over
1. secondary-app: make the DR plan and app the DR target of the workload in the runbook and in the Front Door origin group (priority 2), and take the pair-region app and its origin out of the runbook once TC-1, TC-2, TC-3 and TC-4 have passed.
2. secondary-app: point the data settings of the DR app at the DR region's data services and record the data service playbooks' failover steps as the data part of the runbook.
3. backup-restore: make the DR storage account the source of the restore step in the runbook (restore with Storage as the source), replacing the step that reads from the pair copy of the backup storage.
4. secondary-app-dns: make the DR plan and app the DR target of the workload in the runbook, with the record change in the company's DNS as the traffic switch, and take the pair-region app out of the runbook once TC-1, TC-5, TC-9 and TC-10 have passed.
5. secondary-app-dns: point the data settings of the DR app at the DR region's data services and record the data service playbooks' failover steps as the data part of the runbook.
6. Put the Failover and Failback steps of the chosen option in the runbook with the roles of the option's Build step that grants the roles the Failover and Failback tables use, and mark the DR of the app as Demonstrated only for the times that a drill of the option measured.

### Decommission
1. secondary-app: only after TC-1 to TC-5 passed in the DR region, remove the Front Door origin of the pair-region app, then the pair-region app, then its plan; keep the plan until its last backup and logs have been exported if the team needs them.
2. secondary-app-dns: only after TC-1, TC-5, TC-9 and TC-10 passed in the DR region, remove the pair-region app, then its plan, and any Front Door origin or Traffic Manager endpoint that pointed at it; keep the plan until its last backup and logs have been exported if the team needs them; keep the TXT verification record and the certificate binding of the DR app, which the switch needs.
3. backup-restore: only after TC-7 passed from the DR storage account alone, stop using the RA-GZRS or RA-GRS pair copy as the restore source; change the redundancy of the primary backup storage account only if no other data of that account needs the pair copy (use the playbook of the storage service for the change).
4. Leave the primary plan, apps and backup schedule as they are; nothing in the primary is removed by this migration.

### Keep until cut-over
Today's pair-region app and plan, their Front Door or Traffic Manager origin and the runbook steps that fail over to them; the pair copy of the backup files (RA-GZRS or RA-GRS) and the runbook step that restores from it; and the primary's own custom backup schedule, until the checks listed in Validate for the option have passed.

## Test criteria

### TC-1: The DR app has the same build and settings as the primary
- Applies to: secondary-app, secondary-app-dns
- Pass condition: the build ID that the pipeline deployed to the DR app equals the one on the primary app (this is the check of the Estimated RPO of 0 of the option for application content), and a comparison of the two apps' settings and plans shows zero differences other than the region-specific values that the template lists (endpoints, resource IDs; where Front Door is used, its ID is the same on both): app setting names, runtime stack and version, OS, health check path, access restrictions, autoscale rules, plan tier family, plan zone redundancy intent, and the numbers of custom domains and TLS bindings.
- How to measure: the pipeline's deployment record for both apps, and a scheduled job that reads both apps and plans (CLI or resource graph) and compares them with the template's parameters; a drift is a finding.
- Evidence: the deployment records with the build IDs, and the comparison report with its date and the list of differences with their reason (none expected beyond the list).
- Frequency: after every deployment, and weekly

### TC-2: The DR origin is healthy and direct traffic is blocked
- Applies to: secondary-app
- Pass condition: for 7 consecutive days, the Front Door origin group shows the DR origin as healthy, a probe request from the test source that the extra access rule allows (the only path to the DR origin while the primary origin is healthy, because Front Door sends traffic to the primary origin then) returns the expected status within the latency bound that the team records, and a request straight to the DR app's default host name from outside the allowed sources is refused by the access restriction.
- How to measure: the Front Door origin health and probe metrics, a synthetic availability test that calls the DR app from the allowed test source, and a scheduled request from outside the allowed sources that must be refused.
- Evidence: the daily probe results with the status codes and latencies, the origin health export, and the refused-request log.
- Frequency: daily

### TC-3: Traffic switches to the DR app within the Estimated RTO
- Applies to: secondary-app
- Pass condition: with the primary origin disabled (or unhealthy), the first successful request through the Front Door endpoint that is answered by the DR app comes within the Estimated RTO of the option, the DR plan reaches the target instance count in the time that the team recorded, the application's error rate and response time return to the bounds that the application owner set, and for a non-HTTP-trigger function app exactly one region processes each event.
- How to measure: a drill that disables the primary origin (or blocks its health probe path), times the switch from its start to the first successful request answered by the DR app, records the scale-out time of the DR plan, and counts the events processed per region for a function app.
- Evidence: the drill record with timestamps, the Front Door health and request logs, the instance count over time, and the function trigger logs.
- Frequency: every DR drill, and after every change to Front Door, the DR plan or the pipeline

### TC-4: The DR app's network, identity and domain settings are in place
- Applies to: secondary-app, backup-restore
- Pass condition: for the DR app of secondary-app: virtual network integration and private endpoints are set as planned, the managed identity exists and holds its roles on the DR data services, custom domains and TLS bindings are present and the certificate is valid for at least the period the team sets, the access restriction holds the AzureFrontDoor.Backend service tag and the x-azure-fdid header, and alerts exist. For backup-restore: the template that rebuilds each item on the not-restored list exists and deploys without error into an empty resource group of the DR region, the storage accounts have the settings of Build (versioning, change feed, replication rule), and the DR storage account allows the DR app's access path.
- How to measure: read the app, plan and storage account properties with a read-only query, list the role assignments of the DR app's identity, and for backup-restore deploy the template with a what-if into a scratch resource group in the DR region (no data of the app).
- Evidence: the query output with its date, the role assignment list, the certificate expiry dates, and the template deployment or what-if result.
- Frequency: monthly, and after every change to network, identity or domains

### TC-5: The app keeps no state only on one app's disk
- Applies to: secondary-app, secondary-app-dns
- Pass condition: every kind of data that the app writes is listed with its store, and none is only in the App Service file system of one app (/home, %HOME%) unless the application owner has accepted its loss in DR in writing; every listed store is a data service that is covered by its own playbook for the DR region, or a mounted share whose DR path is recorded (by the inference in the constraint on file-system state, GZRS or GRS reach the pair and not a DR region that is not the pair).
- How to measure: a review of the app's writes (configuration of upload folders, session store, caches, queues, logs), a list of the file-system folders that change during a day, and a check of each store's replication in its own test criteria.
- Evidence: the inventory of writes with the store and DR path of each, and the acceptance record for any accepted loss.
- Frequency: before cut-over, then every release that changes how the app writes state

### TC-6: The newest backup in the DR region is current
- Applies to: backup-restore
- Pass condition: the last custom backup of each app reports success, the size is below the 10 GB limit, the newest complete pair (ZIP and XML) in the DR container is no older than the backup interval plus the largest copy lag that the team recorded in the first week, the replication status of the newest blob is complete, and the replication metrics show no operations pending in the over-24-hour bucket.
- How to measure: the Backups page of each app, a scheduled job that lists the DR container and compares the newest blob's time with the primary's, the object replication status of the newest blob (readable on the source account, which is available while TC-6 runs), and the Operations pending for replication metric of the source account by time bucket.
- Evidence: the daily job report with the backup time, copy time and lag per app, the size, and the metric export.
- Frequency: daily

### TC-7: An app is restored in the DR region from the DR storage alone
- Applies to: backup-restore
- Pass condition: in a drill, a new app in the DR region is restored from the newest backup in the DR storage account (Storage as the source) without reading the primary region's storage, the restore completes, the app starts and answers its health probe, a hash of the restored content folder equals the hash recorded at the backup time, every item of the not-restored list has been rebuilt from the template, and the time from the start to the first successful request is within the Estimated RTO of 24h of the option and is recorded as the Demonstrated recovery time; for a Functions app with Azure Files content storage the drill must show whether the restore works or the app is recovered by redeploy.
- How to measure: a drill that creates a scratch plan and app in the DR region, restores into it, rebuilds the settings from the template, runs the health probe and the content hash, and then deletes the scratch resources; the time is taken from the start to the first successful request.
- Evidence: the drill record with timestamps, the restore log, the hash comparison, the list of rebuilt items and the measured time.
- Frequency: every DR drill, and after every change to the backup configuration, the DR storage or the app's runtime stack

### TC-8: Everything outside the backup has a DR path
- Applies to: backup-restore
- Pass condition: the inventory of the Build step that writes down what is outside the backup lists, for each app, the run-from-ZIP content, the mounted storage, the linked database, the settings on the not-restored list and the Azure Files content storage of a Functions app, and every item has a named DR path (CI/CD redeploy, a data service playbook, a template) that has been exercised in the drill or in its own test criteria; no app has a linked database in its custom backup that is the only copy of the database (the option ends on 31 March 2028).
- How to measure: read each app's configuration (package settings, storage mounts, connection strings, content storage settings) and compare it with the inventory; check each DR path's last test date.
- Evidence: the inventory with the path and last test date per item, and the configuration export with its date.
- Frequency: monthly

### TC-9: The DR app serves the custom domain over a valid certificate
- Applies to: secondary-app-dns
- Pass condition: the custom domain is listed on the DR app with a TLS binding to a certificate that covers the name, is signed by a trusted certificate authority and stays valid for at least the period the team sets; the TXT verification record of the DR app exists in the company's DNS; a request to the custom domain from a test client that resolves the name to the DR app's entry point returns the expected status over that certificate within the latency bound the team records; and the DR app's virtual network integration, private endpoints, access restrictions, managed identity with its roles on the DR data services, and alerts are as planned.
- How to measure: read the DR app's host name bindings and certificates (with their expiry dates), resolve the TXT record on the company's DNS, run a scheduled request from the test client with the name pinned to the DR entry point, and list the role assignments of the DR app's identity.
- Evidence: the daily request results with status, certificate and latency, the binding and certificate export with expiry dates, the TXT lookup and the role assignment list.
- Frequency: daily for the request; monthly and after every change to network, identity, domains or certificates for the configuration

### TC-10: Traffic switches to the DR app through the company's DNS within the Estimated RTO
- Applies to: secondary-app-dns
- Pass condition: in a drill, the time from the failover decision to the first request through the custom domain from a client network that the DR app answers, which includes the record change and the TTL wait, is within the Estimated RTO of the option; the authoritative company DNS returns the DR entry point right after the change; after the TTL every client network the team tests resolves the name to the DR entry point; the DR plan reaches the target instance count in the time the team recorded; the error rate and response time return to the bounds that the application owner set; and for a non-HTTP-trigger function app exactly one region processes each event.
- How to measure: a drill with the primary treated as unreachable that records the time of the decision, of the record change, of the end of the TTL and of the first successful request per client network, resolves the name on the authoritative company DNS and from each client network, records the instance count of the DR plan over time, and counts the events processed per region for a function app.
- Evidence: the drill record with timestamps, the resolution results per client network, the request logs of the DR app, the instance count over time, and the function trigger logs.
- Frequency: every DR drill, and after every change to the record, its TTL, the DR plan or the pipeline
