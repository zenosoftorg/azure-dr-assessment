# Azure Cache for Redis and Azure Managed Redis

This playbook covers two ARM types: `microsoft.cache/redis` (Azure Cache for Redis) and `microsoft.cache/redisenterprise` (Azure Managed Redis and the Enterprise tiers of Azure Cache for Redis). The mechanisms and constraints say which one applies to which.

## Mechanisms

### Geo-replication
- Replicates: the data of the cache to a linked cache instance in another region, with user-controlled failover. Learn's high availability article lists it as one option with two forms: passive geo-replication on the Premium tier (`microsoft.cache/redis`: two linked caches, a primary that serves reads and writes and a secondary that receives the replicated data) and active geo-replication on the Enterprise tiers (`microsoft.cache/redisenterprise`: up to five instances in different regions that the application reads from and writes to through their own endpoints, with conflict-free replicated data types to merge writes). The constraints give the same for Azure Managed Redis
- Paired: yes
- Nonpaired: yes
- Failover: customer-managed
- Estimated RPO: unknown (Learn publishes no figure for either form; the constraints on passive and active replication give its wording, and TC-2 measures the lag that the team accepts)
- Estimated RTO: unknown (Learn describes no Microsoft-triggered cross-region failover: the customer starts the failover, and for the active form also redirects the application; the constraints give Learn's wording for each form, and TC-3 times the switch-over)
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-high-availability

### Import and export
- Replicates: a snapshot of the cache data as a Redis Database (RDB) file in a blob of an Azure Storage account, on demand and not continuously. Learn's reliability article for Azure Managed Redis says the service has no built-in import or export scheduler, that the customer can develop automation with the Azure CLI or Azure PowerShell to start exports, that exported files can be restored to the same or to a different cache instance, and that the storage account can use geo-redundant storage (GRS) in supported regions or the backup blobs can be copied or moved to other locations. The constraints give the rules of the other tiers
- Paired: yes
- Nonpaired: yes
- Failover: manual
- Estimated RPO: unknown (data written after the last export is not in the file; the export interval comes from the automation the customer builds, so the team sets it and TC-7 proves it)
- Estimated RTO: unknown (Learn publishes no import time)
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-managed-redis#backup-and-restore

### Delete and recreate cache
- Replicates: nothing. Learn's guidance for a regional outage is to consider recreating the cache in a different region and updating the application to connect to the new cache, and it says that data is lost during a regional outage, that the application code should be resilient to data loss, and that the unavailable cache is automatically restored once the affected region is restored. It lists the Standard, Premium, Enterprise and Enterprise Flash tiers
- Paired: yes
- Nonpaired: yes
- Failover: manual
- Estimated RPO: unknown (Learn: "data is lost during a regional outage"; what survives is whatever the customer exports or reloads from its source of truth)
- Estimated RTO: unknown (Learn publishes no total for recreating a cache and switching the application; TC-8 times it)
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-high-availability#delete-and-recreate-cache

## Constraints

### Which product uses which ARM type
Learn's private endpoint DNS reference lists Azure Cache for Redis under `Microsoft.Cache/Redis`, and Azure Cache for Redis Enterprise and Azure Managed Redis under `Microsoft.Cache/RedisEnterprise`, with a different private DNS zone for each: privatelink.redis.cache.windows.net, privatelink.redisenterprise.cache.azure.net and privatelink.redis.azure.net.
- Source: https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns#commercial

### Azure Cache for Redis has a retirement timeline
Learn's Azure Cache for Redis pages announce a retirement timeline for all SKUs and recommend moving existing instances to Azure Managed Redis as soon as possible, with migration guides for the Basic, Standard and Premium tiers and for the Enterprise tier. The migration guides are not part of this playbook. This means a DR build for a cache that is about to move should be made for the product it moves to.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication

### Passive geo-replication is a Premium feature
Passive geo-replication is only available in the Premium tier of Azure Cache for Redis. Basic and Standard do not offer it, and the Enterprise and Enterprise Flash tiers offer active geo-replication instead. It creates an active-passive relationship: only the primary is written to, and the secondary is read-only. Learn says passive geo-replication is designed as a disaster-recovery solution.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication#scope-of-availability

### Passive geo-replication is not tied to the paired region
Learn says the instances are "typically located in different Azure regions, though that isn't required", and its prerequisites (Premium tier, one replica per primary per shard, the same subscription, a secondary of the same or a larger size, both caches running, the same Redis server version) name no pairing condition. Its advice for the secondary is to place it in the same region as the application that accesses it, and, for applications with separate primary and fallback regions, to place the primary and secondary caches in those regions. This means a DR region that is not the pair is a supported choice for this form. Learn does not state it in those words, so Azure reality (the Compatible caches list when linking) decides.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication

### Passive geo-replication prerequisites and restrictions
Both caches must be Premium, in the same Azure subscription, created and running, on the same Redis server version, with one replica per primary per shard. The secondary must be the same size or larger, and to use geo-failover both caches must be the same size. Clustering is supported if both caches have clustering enabled with the same number of shards. Persistence is not supported with geo-replication. While linked, the secondary is read-only, neither cache can be scaled, the number of shards cannot be changed, nothing can be imported into the secondary, and neither cache nor its resource group can be deleted until the caches are unlinked. Data that was in the secondary before the link is removed. When the link is removed, the replicated data stays in the secondary and the secondary accepts reads and writes once the unlinking completes. Failover is not automatic: "You must start the failover from the primary to the secondary linked cache." Data transfer between regions is charged at standard bandwidth rates.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication#geo-replication-prerequisites

### Passive geo-replication links exactly two caches
Learn says only two caches can be linked with passive geo-replication, whereas active geo-replication supports up to five. This means a cache in a new DR region can be linked to a Premium primary only after the earlier secondary has been unlinked, which leaves a period without a linked secondary.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication#can-i-link-more-than-two-caches-together

### Passive geo-replication: private links and firewalls
Private links cannot be added to caches that are already geo-replicated: unlink the geo-replication, add the private link, then relink. A cache with a firewall needs the secondary cache's IP address in the primary cache's firewall rules, and a firewall is not supported on a cache whose public network access is disabled and that uses only a private endpoint.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication

### Passive geo-replication and zone redundancy
Learn's move guide lists "Zone Redundancy isn't supported with geo-replication" among the features that geo-replication does not support. The geo-replication article itself does not list zone redundancy, so check the zone setting of a cache, and that it appears in the Compatible caches list, before linking it.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-moving-resources#passive-geo-replication-premium

### Passive geo-replication is continuous and asynchronous and guarantees no recovery point
Replication is incremental, asynchronous and continuous, on no schedule, and the time taken "isn't much different from the latency across regions". The secondary may need a full sync, which depends on load, bandwidth and inter-region latency; Learn's finding for a full 53-GB geo-replicated pair is "anywhere between 5 to 10 minutes". For a geo-replicated cache persistence is disabled. If the pair is unlinked the secondary keeps the data synced up to then and "No recovery point is guaranteed". To obtain a recovery point, export from either cache.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication

### Passive geo-replication metrics
Geo Replication Healthy shows the link status (unhealthy if either cache is down), Geo Replication Connectivity Lag the time since the last successful synchronisation, Geo Replication Data Sync Offset the data yet to be synchronised to the secondary, and the Fully Sync Event Started and Finished events a full sync. Learn recommends the prebuilt Geo-Replication Dashboard workbook.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication#can-i-track-the-health-of-the-geo-replication-link

### Passive geo-failover is one operation and takes a few minutes
A geo-failover is triggered with one select: the geo-secondary is promoted to geo-primary, the DNS records of the geo-primary URLs are updated (the geo-primary URL, of the form cachename.geo.redis.cache.windows.net, stays the same and always points to the current geo-primary), and the old geo-primary is demoted to secondary and tries to link to the new geo-primary. Learn says the process takes a few minutes, and that once the link status shows Creating the new geo-primary accepts reads and writes. Before a failover, the firewall settings, the port and the TLS settings of both caches must be alike, and because the caches have different access keys the application must be able to switch keys, or use Microsoft Entra tokens, which Learn recommends for geo-failover.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication#initiate-a-failover-from-geo-primary-to-geo-secondary

### Passive geo-failover with minimal data loss
For a planned failover Learn advises: check the Geo Replication Data Sync Offset metric on the current geo-primary and, "If possible", initiate the failover only when fewer than 14 bytes remain to be written; run `CLIENT PAUSE` on the current geo-primary before the failover with a timeout long enough for it (around 30 minutes, 1,800,000 milliseconds, is a place to start). There is no need to run `CLIENT UNPAUSE`, because the new geo-primary retains the pause. Failover can introduce data inconsistencies, especially if a client keeps a connection to the old geo-primary during it.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-geo-replication#failover-with-minimal-data-loss

### Passive geo-replication: a region outage is handled by unlinking
Learn's high availability article lists Geo-replication with Passive for the Premium tier and Active for the Enterprise tier. With the ARM type mapping above, this means passive geo-replication belongs to `microsoft.cache/redis` Premium caches and active geo-replication to `microsoft.cache/redisenterprise` caches. The same article says that if the region hosting the primary cache goes down, the failover starts by unlinking the secondary cache and then updating the application to point to the secondary cache for reads and writes.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-high-availability

### Active geo-replication links instances in any regions where the service is available
For Azure Managed Redis Learn says active geo-replication can be set up "between any Azure regions where the service is available", so the DR region need not be the pair. All instances of a replication group must use the same tier and size and identical settings, including persistence options, modules and clustering policies. Learn also says you pay for each instance in every region of the group and might incur data transfer charges between regions.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-managed-redis#requirements-1

### Active geo-replication needs a supported SKU and a high availability configuration
For Azure Managed Redis, active geo-replication is available on the Memory Optimized, Balanced and Compute Optimized tiers except the Balanced B0 and B1 SKUs, and is not available on the Flash Optimized tier. It is only supported when the cache is in a high availability configuration (that is, it uses replication).
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication#scope-of-availability

### Active geo-replication on the Enterprise tiers excludes E1 and Flash SKUs
For Azure Cache for Redis Enterprise the prerequisites say active geo-replication is not supported on E1 and any Flash SKUs, although the availability table of the same page marks Enterprise and Enterprise Flash as available. This playbook follows the stricter prerequisite, so an E1 or Flash cache has no geo-replication option and rebuild-in-dr applies; Azure reality decides.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-active-geo-replication#active-geo-replication-prerequisites

### Active geo-replication needs identical configuration and limits modules and persistence
For Azure Managed Redis all caches of a group must have the same configuration, for example the same SKU, capacity, eviction policy, clustering policy, modules and TLS setting. Only the RediSearch and RedisJSON modules are supported and data persistence is not supported. A group holds up to five instances. If one instance is scaled, the others must be scaled to the same size before any other scaling can occur.
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication#active-geo-replication-prerequisites

### Active geo-replication syncs with eventual consistency and has no SLA on sync time
Learn says data sync among replicas follows eventual consistency, that "The service does not provide SLA on sync time", and that systems should be designed without relying on the timeliness of data sync. Writes to one instance are automatically reflected in the others in the group. The same page says the bandwidth charges of this inter-region data transfer are currently absorbed by Azure Managed Redis and not passed on to customers, and that billing can change.
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication

### With active geo-replication the customer routes traffic and fails over
Azure Managed Redis does not route traffic between regions: the application connects to a specific instance, and implements health checks, circuit breaker patterns or external load balancing to detect a region failure and move to a healthy instance. Learn says "you're responsible for failover between cache instances", that failover "involves preparation and might require you to do multiple steps", and that the downtime "typically ranges from seconds to a few minutes" depending on the application's health check and failover configuration. Asynchronous replication can lose recent writes to a failed region that had not replicated, depending on the replication lag at the time. Microsoft does not automatically notify the customer of a region failure; Azure Service Health alerts are the way to learn of it.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-managed-redis

### Active geo-replication: force unlink during a region outage
If a cache of the group is down, metadata builds up in all caches of the group, because it cannot be discarded until writes can sync to all caches, and the available caches might run out of memory. Learn says force unlinking the cache that is down prevents the build-up, and to consider monitoring available memory and unlinking if there is memory pressure, especially for write-heavy workloads. The procedure is: select an available cache, open Active geo-replication, check the cache to force-unlink, select Force unlink and confirm. Once the affected region's availability is restored, the affected cache has to be deleted and recreated to add it back to the group.
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication#force-unlink-if-theres-a-region-outage

### Active geo-replication: a recovered region rejoins on its own
When a failed region recovers, Learn says Azure Managed Redis automatically reintegrates its instances into the group, syncs the changes from healthy instances and makes them fully active, and that the customer reconfigures the application to route traffic back to the recovered instance. This describes an instance that stayed in the group; for one that was force-unlinked, the previous constraint applies.
- Source: https://learn.microsoft.com/en-us/azure/reliability/reliability-managed-redis#region-recovery

### Active geo-replication: adding an existing instance discards its data
An existing instance is added to a group with the REST API force-link action: all data in the instance being linked is discarded, the instance is unavailable for several minutes, and portal and CLI support are not yet available for it. A new instance can join a group when it is created, on the Active geo-replication tab, or with the group nickname and the linked databases in the CLI and PowerShell create commands.
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication#add-an-existing-instance-to-an-active-geo-replication-group

### Active geo-replication: flush, health metric and sync issues
`FLUSHALL` and `FLUSHDB` cannot be used in a group. The flush operation removes the data from the current cache and from all linked caches, and Learn says to give access to it only to authorised users through Azure RBAC. The Geo Replication Healthy metric emits 0 when unhealthy; Learn recommends an alert when it is 0 continuously for at least 60 minutes, because it can show unhealthy temporarily for maintenance or scaling. Learn lists custom hashtags, large keys (keep keys under 500 MB; near 2 GB the cache faces health issues) and out-of-memory as causes of sync problems, and says syncing pauses under memory pressure.
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-active-geo-replication

### Azure Managed Redis authentication and access keys on geo-replicated caches
Azure Managed Redis uses Microsoft Entra authentication by default. The user or service principal is added to each cache (the Authentication pane), the client acquires a token with the scope that Learn gives for Redis (redis.azure.com/.default), uses the object ID of the identity as the user, and refreshes the token before it expires. Disabling access keys terminates all existing client connections, and on geo-replicated caches the caches must first be unlinked, the keys disabled and the caches relinked.
- Source: https://learn.microsoft.com/en-us/azure/redis/entra-for-authentication

### Azure Managed Redis private endpoints
Applications connect to the host name of the form cachename.region.redis.azure.net on port 10000, and a private DNS zone named *.privatelink.redis.azure.net is created automatically and is needed for the TLS connection. For endpoints in several virtual networks the private DNS zone must be configured manually for them before the endpoint is created. If the endpoint is in another subscription than the cache, the Microsoft.Cache resource provider must be registered in that subscription. Deleting all private endpoints puts the cache on public network access.
- Source: https://learn.microsoft.com/en-us/azure/redis/private-link

### Import and export: Azure Cache for Redis
Export writes an RDB snapshot to a blob and the cache stays available; import loads RDB files, deletes existing data and makes the cache inaccessible to clients while it runs. Import and export are available on the Premium, Enterprise and Enterprise Flash tiers (not Basic and Standard). To import, the RDB files must be in blobs in the same region and subscription as the cache (with managed identity for the storage account the subscription can differ). Blob storage accounts and Azure Data Lake Storage Gen2 accounts do not support export, and Enterprise and Enterprise Flash do not support storage accounts that use firewalls or private endpoints. Files from Premium can be imported into the Enterprise tiers but not the reverse, and a backup from a newer Redis version cannot be imported into an older one. Persistence is a durability feature: on Premium its file cannot be imported into a different cache, and on the Enterprise tiers it is on a disk that the user cannot access.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-how-to-import-export-data

### Import and export: Azure Managed Redis
Azure Managed Redis exports as a .gz block blob and imports from a page or block blob; storage accounts with firewalls or private links are not supported; import makes the cache unavailable and deletes its existing data; individual keys larger than 2 GB make an import fail; RDB files from a newer Redis version cannot be imported into an older one. The shared access signature of the container needs read, add, create, write, delete, tag and move permissions for export, and read, add, create and list for import.
- Source: https://learn.microsoft.com/en-us/azure/redis/how-to-import-export-data

### A new cache in another region is the simplest move
Learn's move guide says that if the data need not be kept, the easiest way to move regions is to create a new cache in the target region and connect the application to it, for example a look-aside cache of database records that can be rebuilt. The Premium tier lists geo-replication among its options for a move, and the Enterprise tiers list a new cache, an RDB export and import, or programmatic migration. A new cache deployment takes several minutes, and Learn recommends a private endpoint and Microsoft Entra authentication on it.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-moving-resources

### Azure Managed Redis publishes no committed RPO or RTO figure
Learn's reliability planning page says "Azure Managed Redis doesn't publish a guaranteed RPO or RTO, and the service's SLA covers connectivity to the cache endpoint, not protection from data loss", and asks to treat its typical behaviors as design inputs and not commitments. For a region failure with active geo-replication it says the downtime "depends on how quickly your application detects the failure and redirects traffic, typically ranging from seconds to a few minutes", and that "You can lose writes that didn't replicate out of the failed region before the outage, and the potential loss scales with replication lag at the time of failure". For a region failure without active geo-replication it says there is "no platform-managed regional failover", so the recovery time and the recovery point depend on how recently a backup was exported and how quickly a new instance is provisioned and the export imported. So no RPO or RTO number of this playbook is a Learn figure: the values are team-set starting values that TC-2, TC-3, TC-7 and TC-8 prove.
- Source: https://learn.microsoft.com/en-us/azure/redis/plan-reliability-and-durability#rpo-and-rto-considerations

## Non-paired options

### geo-replication: Link a cache in the DR region with geo-replication
- Kind: native
- Target: dr-region
- Uses mechanism: Geo-replication
- Estimated RPO: 15m (Estimated, team-set starting value for the replication-lag bound; TC-2 proves it. Both forms replicate asynchronously, so the value is never 0, and Learn publishes no figure: the passive form guarantees no recovery point after an unlink, the active form has no SLA on sync time, and for Azure Managed Redis "the potential loss scales with replication lag at the time of failure" — https://learn.microsoft.com/en-us/azure/redis/plan-reliability-and-durability#rpo-and-rto-considerations)
- Estimated RTO: 15m (Estimated, team-set starting value for the switch-over from the declaration to the first successful write; TC-3 proves it. Learn: the passive geo-failover process takes a few minutes; for the active form the downtime "typically ranges from seconds to a few minutes" and depends on how quickly the application detects the failure and redirects traffic — https://learn.microsoft.com/en-us/azure/redis/plan-reliability-and-durability#rpo-and-rto-considerations; the detection and the decision are the team's)
- Prerequisites: a Premium cache (passive form) or an Azure Managed Redis or Enterprise cache on a SKU that supports active geo-replication (active form), with the same tier, size and settings in the DR region. Passive form: same subscription, same Redis version, one replica per primary per shard, no persistence, the same shard count when clustered, the same size for geo-failover, and the DR cache created, with its private endpoint and firewall rules, before the link. Active form: identical settings across the group (same SKU, capacity, eviction policy, clustering policy, modules and TLS setting) and no module other than RediSearch and RedisJSON; for Azure Managed Redis also a high availability configuration and the DR instance created into the group (Learn: a REST force-link on an existing instance discards its data), and for Enterprise the DR instance created into the group from the Advanced tab of the create form or the group nickname and linked databases of the CLI or PowerShell. Networking: a private endpoint for each DR cache in the DR virtual network, with the private DNS zone of the product (see the first constraint) linked to every virtual network that runs DR consumers. Identity: for Azure Managed Redis the DR workload's managed identity added as a user of each cache with Microsoft Entra authentication (each cache has its own access key); for Premium Learn recommends Microsoft Entra tokens for geo-failover, and for Premium and Enterprise caches the pages read describe no steps for adding a user, so the team records how the DR workload authenticates to each cache and TC-6 proves it; operators with write rights on the caches of both regions and on private endpoints and DNS links in the DR network (the pages read for this playbook name no built-in role, so the team chooses one and records it); nobody holds flush rights by default. Application: both cache endpoints as deployment parameters, retries with backoff, cache-aside behaviour where the data allows it and, for the active form, its own failover logic.
- Cost notes: a second cache of the same size in the DR region, and every instance of an active group is billed; cross-region data transfer charges apply (see the constraints, including what Learn says about Azure Managed Redis currently absorbing them); no price.
- Gives up: automatic failover (the customer starts it and, for the active form, redirects the application); a recovery point that Learn promises, and any SLA on sync time; for the passive form writes to the secondary before promotion, persistence, scaling while linked, a change of shard count, a third cache and zone redundancy; for the active form persistence, `FLUSHALL` and `FLUSHDB`, modules other than RediSearch and RedisJSON, the Flash SKUs, B0, B1 and, on Enterprise, E1, and strong consistency (eventual consistency).
- Recommended when: the cache holds data that cannot be rebuilt quickly from a source of truth, or the load of a cold start on that source is not acceptable, and the tier and SKU support the geo-replication form of its family.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-high-availability

### rebuild-in-dr: Standby cache in the DR region, loaded from an export or from the source of truth
- Kind: workaround
- Target: dr-region
- Uses mechanism: Delete and recreate cache
- Estimated RPO: 24h (Estimated, team-set starting value for the export interval, to confirm against the value of the data; TC-7 proves it. Learn publishes no interval and the file holds only the data of the last export; for a pure cache-aside cache the source of truth is the recovery point)
- Estimated RTO: 1h (Estimated, team-set starting value for the switch-over time the team designs for readying or creating the DR cache, importing the file if one is used and switching the application; TC-8 proves it. Learn says a new cache deployment takes several minutes and publishes no import time)
- Prerequisites: the tier decides what the option can carry. Premium, Enterprise, Enterprise Flash and Azure Managed Redis support export and import; Basic and Standard do not, so for them the option rebuilds from the source of truth only (a new cache, no data seeded). An infrastructure template of the cache (tier, size, shard count, Redis version, clustering policy, modules, eviction policy, TLS, authentication) with the region as a parameter, so that the DR cache is the same product with a Redis version no older than the exported file's. Where an export is used: a storage account in the DR region for the exported files (Learn requires the file to be in the same region and subscription as the importing cache for Azure Cache for Redis and states no region rule for Azure Managed Redis; this playbook keeps it in the DR region for both), without a firewall or private endpoint for Enterprise tiers and Azure Managed Redis (a security trade-off for the owner of the data to accept or reject), and never a Blob storage account (or, for Azure Cache for Redis, a Data Lake Storage Gen2 account); a scheduled export of the primary (Learn says Azure Managed Redis has no built-in scheduler, and for Azure Cache for Redis that a script can trigger the export periodically) and a copy job into the DR storage (Learn suggests a geo-redundant storage account for the exported data); for failback a storage account in the primary region with the same rules, because Azure Cache for Redis imports only files in the region and subscription of the importing cache (the same placement is kept for Azure Managed Redis as a design choice); storage rights for the identity that runs the export, copy and import (the shared access signature or managed identity permissions that Learn lists). Also the private endpoint, DNS link and authentication of the DR workload in the DR region as for geo-replication, and an application that works cache-aside, with a source of truth that can take the load of a cold cache.
- Cost notes: the storage for the files and their copies, the export and copy runs, and either a standby cache in the DR region that is billed while idle, or no standby and a longer RTO because the cache is created at failover time; no price.
- Gives up: continuous replication (data written after the last export is lost); automatic failover; any recovery point that Learn states; for Basic and Standard any data at all (they have no export); for Enterprise tiers and Azure Managed Redis a storage account with a firewall or private endpoint. Learn's delete-and-recreate section lists the Standard, Premium, Enterprise and Enterprise Flash tiers and not Basic or Azure Managed Redis; this playbook applies the same approach to them as a design assumption, on the strength of the move guide's "Create a new cache (All tiers)".
- Recommended when: the cache can be rebuilt from its source of truth (always the case for Basic and Standard), or its SKU has no geo-replication (E1, Flash, B0, B1), or a second billed cache is not justified by the data.
- Source: https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-high-availability#delete-and-recreate-cache

## Migration from a paired setup

### Recognise today's setup
Learn names no pairing requirement for passive or active geo-replication (see the constraints), so a paired setup is a choice. Record a DR relationship only when it is observed in the inventory or confirmed by the owner of the workload; the existence or absence of a cache in the pair region proves nothing, and a cache's name or location says nothing about what it is for. Observed means: a `microsoft.cache/redis` Premium cache whose Geo-replication pane lists a linked cache (the server link; Learn names the `az redis server-link` command group) is passive geo-replication, and a `microsoft.cache/redisenterprise` cache of an Azure Managed Redis or Enterprise SKU that belongs to a replication group (a group nickname and linked databases) is active geo-replication; the DR region of the setup is the region of the linked cache or of the other group members, and it is paired DR when that region is the pair of the primary's region. A setup that rebuilds from exports or from the source of truth is not visible in an inventory (a scheduled export or a standby cache is not a resource property): record it only when the owner confirms it, with the confirmation. A cache with no observed link and no confirmation is Unknown, not "no DR copy". For every cache record the product, tier or SKU, size, shard count, replica count, Redis version, persistence, zone redundancy, clustering policy, modules, eviction policy, TLS setting, network access and authentication (Microsoft Entra or access keys). The option is chosen per cache and recorded by option id; one workload can mix them, never on one cache.

### Build
1. Take the inventory above for every cache of the workload, check that the product and SKU are offered in the DR region, and choose the option per cache: geo-replication for a Premium cache and for an Azure Managed Redis or Enterprise cache whose SKU supports active geo-replication, rebuild-in-dr for the others and for a cache whose data does not justify a second billed cache. Record with the application owner how much data loss it accepts and whether it is cache-aside; the Estimated RPO bound comes from it.
2. geo-replication: for Premium, create the DR cache in the DR region with the same size, shard count, Redis version and clustering as the primary, one replica per primary per shard, no persistence, in the same subscription, and with the zone setting that lets it appear in the Compatible caches list. Add its private endpoint in the DR virtual network, the private DNS zone link and the firewall rules (the secondary's IP address in the primary's firewall rules when a firewall is used) now, because a private link cannot be added to a cache that is already geo-replicated. Do not link it yet.
3. geo-replication: for Azure Managed Redis and Enterprise, create the new instance in the DR region with the same tier, size, clustering policy, modules, eviction policy and TLS setting as the other members, and join it to the existing group when creating it. Azure Managed Redis: a high availability configuration, and on the Active geo-replication tab Join existing group (or the group nickname and the linked databases of every member in the CLI or PowerShell create command); never use the REST force-link on an instance that holds data, because it discards the data. Enterprise: on the Advanced tab of the create form select Configure to set up Active geo-replication and choose the existing group (or use the same CLI or PowerShell parameters). The pair-region member stays in the group (up to five instances) until Decommission.
4. Build the private access in the DR region: a private endpoint for each DR cache in the DR virtual network, the private DNS zone of the product linked to every virtual network that runs DR consumers (for Azure Managed Redis Learn says to configure the zone for several networks before creating the endpoint, and to register the Microsoft.Cache resource provider in the endpoint's subscription when it differs from the cache's; the same is sensible for the other products but is not stated for them), name resolution for on-premises callers where they exist (a design assumption that the DNS reference page does not cover), and public network access as planned.
5. Build the identity. Azure Managed Redis: add the DR workload's managed identity as a user of each DR cache (the object ID of the identity is the user name) and set the application to acquire Microsoft Entra tokens and refresh them before they expire. Premium and Enterprise: Learn recommends Microsoft Entra tokens for Premium geo-failover and describes no add-user steps on the pages read, so record how the DR workload authenticates to each cache (Microsoft Entra where the cache supports it, else the access key), which TC-6 proves; where access keys stay, store the keys of each cache in the DR configuration. Give the Platform engineer role write rights on the cache resources of both regions (link, unlink, force unlink, failover, create, delete), the right to create private endpoints and DNS links in the DR network, and a credential that may run `CLIENT PAUSE` on both Premium caches (each is the geo-primary after a failover); give flush rights to no role.
6. geo-replication: configure monitoring: for the active form an alert on Geo Replication Healthy at 0 for at least 60 minutes (the window Learn recommends for the active form) and an alert on the memory use of every instance; for Premium an alert on Geo Replication Healthy with an observation window the team sets (Learn gives no value or window for Premium), alerts on Connectivity Lag and Data Sync Offset with bounds the team sets (the Estimated RPO parameter that TC-2 proves) and the Geo-Replication Dashboard workbook; and Service Health alerts for the primary and DR regions.
7. geo-replication: configure the application: both cache endpoints as deployment parameters per region, no address in code, retries with backoff, cache-aside fallback to the source of truth; for the active form its own failover logic (health check and circuit breaker, or an external load-balancing service); for Premium decide whether it uses the endpoint of each cache or, for a planned failover only, the geo-primary URL (Learn describes that URL only while the caches are linked, so it is not the route after an unlink), and test the choice in TC-3.
8. geo-replication: for Premium, export the primary as a recovery point (export is allowed from either cache and the cache stays available), then in the agreed window unlink the secondary in the pair region (only two caches can be linked, so this starts a period without a linked secondary: note its start time) and link the DR cache from the Geo-replication pane of the primary (Add cache replication link, choose the DR cache from the Compatible caches list, Link). The unlinked pair-region cache keeps its synced data and is the rollback source. Wait for the link provisioning status Succeeded; the primary stays available during the link and the DR cache does not until it completes.
9. rebuild-in-dr: deploy the DR cache from the template in the DR region (a standby, or only the template and a pipeline when no standby is kept), with its private endpoint, DNS link and authentication as in the Build steps that build the private access and the identity. Where the cache supports export (not Basic or Standard): create the DR storage account and, for failback, a storage account in the primary region (see Prerequisites of the option) with the roles for export, copy and import in both regions, build the scheduled export of the primary, the copy into the DR storage at the interval the team sets (the Estimated RPO parameter that TC-7 proves) and an alert on the age of the newest file in the DR storage. For Basic and Standard record that the source of truth is the only recovery point.
10. rebuild-in-dr: configure the application: both cache endpoints as deployment parameters, cache-aside behaviour with fallback to the source of truth while the DR cache is cold, and a throttle or warm-up so that a cold cache does not overload the source of truth; record the capacity of the source of truth for that load with its owner.

### Validate
1. Run TC-1 on every DR cache (weekly, and after every change), then TC-6 from the DR network with the DR workload's identity (weekly, and after every change).
2. geo-replication: run TC-2 for 7 consecutive days and keep its alert and probe running (continuous, reviewed weekly).
3. geo-replication: run TC-3 in a drill (every DR drill): for the Premium form a planned geo-failover with `CLIENT PAUSE` between two healthy caches of the same size, for the active form a redirect of the application to the DR instance with the primary region healthy and no force unlink; then TC-4 to return (every DR drill).
4. geo-replication: run TC-5 on a rehearsal pair or group of the same product and tier that holds no production data (every DR drill), and complete its design check.
5. rebuild-in-dr: run TC-7 (freshness daily, restore test monthly) and TC-8 in a drill (every DR drill).
6. Record each result with its date; a time or figure that a drill measured is Demonstrated, and everything else, including the behaviour in a real regional outage, stays Estimated or Unknown.

### Cut over
1. geo-replication: make the DR cache the DR cache of the application in the runbook and in the DR deployment's configuration, and put the Failover steps for geo-replication (planned failover, region-outage steps, and for the active form the redirect) in the runbook with their owners.
2. rebuild-in-dr: make the DR cache and its storage the DR targets in the runbook, put the Failover steps for rebuild-in-dr in it, and write the data-loss window (the export interval) and its owner in it.
3. Remove the runbook steps that pointed DR at the cache in the pair region.

### Decommission
1. geo-replication: for Premium, after TC-1 to TC-6 passed on the new link, delete the unlinked cache in the pair region (it was unlinked in the Build step that unlinks the secondary in the pair region and links the DR cache, and a linked cache cannot be deleted), with its private endpoint, DNS link and alerts.
2. geo-replication: for Azure Managed Redis and Enterprise, after TC-1 to TC-6 passed, remove the member in the pair region by deleting that instance (the remaining instances reconfigure themselves), then its private endpoint, DNS link and alerts. Do not force unlink it: a force-unlinked cache has to be deleted and recreated to rejoin.
3. rebuild-in-dr: after TC-7 and TC-8 passed, delete the old standby in the pair region and the stored files there.

### Keep until cut-over
For geo-replication on Azure Managed Redis and Enterprise: the member in the pair region stays in the group, with its private endpoint and the application's route to it, until TC-1 to TC-6 have passed. For geo-replication on Premium: the pair-region cache cannot stay linked once the DR cache is linked (only two caches can be linked), so keep it, unlinked with its synced data, as the rollback source until TC-1 to TC-6 have passed, together with the export taken before the unlink. For rebuild-in-dr: the existing standby, the stored files and the runbook steps for them stay until TC-7 and TC-8 have passed.

## Test criteria

### TC-1: The DR cache is configured as planned
- Applies to: geo-replication, rebuild-in-dr
- Pass condition: each DR cache exists in the DR region with the tier or SKU, size, shard count, clustering policy, Redis version, modules, eviction policy and TLS setting recorded in the inventory (and, for a group or pair, the same as its peer); its private endpoint connection is Approved, its host name resolves to the private IP address from every DR network that runs consumers, and its private DNS zone is the one of the product and is linked to those networks; the DR workload's identity has access to the cache as recorded in Build; no role holds flush rights by default; a Geo Replication Healthy alert (active form: 60 minutes at 0; Premium: the window the team sets) and a Service Health alert exist where the option uses geo-replication.
- How to measure: read the cache properties with a read-only query or in the portal and compare them with the inventory and the peer; resolve the host name from inside each DR network; list the private endpoint connections, DNS links, cache users, role assignments of the cache scope and alert rules.
- Evidence: the query output and the job report with their date, the resolved addresses, the user and role lists and the alert list, per cache.
- Frequency: weekly, and after every change to the DR cache, its network, its identity or the application's cache configuration

### TC-2: Replication is healthy and its lag stays inside the bound the team sets
- Applies to: geo-replication
- Pass condition: for 7 consecutive days the replication is healthy, except for maintenance windows shorter than the observation window (60 minutes for the active form, as Learn recommends; for Premium the window the team sets in Build), and the lag stays below the bound the team sets for the Estimated RPO (starting value 15m, Estimated). Premium: the link provisioning status is Succeeded, Geo Replication Healthy is healthy, Connectivity Lag and Data Sync Offset stay below the team's bounds, and every Fully Sync Event Started is followed by a Finished event. Active form: Geo Replication Healthy is healthy for every instance and a canary key written in one region is read with the same value in the others within the bound the team sets (Learn publishes no sync time, so the bound is the team's), and the memory use of every instance stays below the team's alert threshold. The bound is recorded with the probe.
- How to measure: Azure Monitor metrics and alerts for the Geo Replication metrics of each cache, the Geo-Replication Dashboard workbook for Premium, and for the active form a scheduled probe that writes a time-stamped canary key in one region, reads it from the others and records the delay.
- Evidence: the 7-day metric export and the probe log with the delay per sample and its maximum, per pair or group; for a drilled or real failover, the lag at the moment of the failover.
- Frequency: continuous alert and probe, reviewed weekly

### TC-3: The application works from the DR cache after a failover
- Applies to: geo-replication
- Pass condition: in a drill, after the Failover steps, the application in the DR region reads and writes through the DR cache over its private endpoint with its own identity, no write goes to a read-only secondary, the canary key written before the drill and the keys the application needs to start are present, and the switch-over from the declaration to the first successful write completes within the switch-over time the team sets for the Estimated RTO (starting value 15m, Estimated). For Premium the drill is a planned geo-failover with `CLIENT PAUSE` between two healthy caches of the same size; for the active form it is the redirect of the application to the DR instance with the primary region healthy and no force unlink.
- How to measure: a drill that runs the Failover steps for the option and times them from the declaration to the first successful write; compare a canary key and a sample of keys before and after; read the application's cache errors and the cache's connection and error metrics.
- Evidence: the drill record with its timestamps and measured time, the application log, the key comparison and the metric export.
- Frequency: every DR drill, and after every change to the cache tier, size or networking, or to how the application selects its cache

### TC-4: Failback restores replication and the primary route
- Applies to: geo-replication
- Pass condition: after the Failback steps the primary-region cache serves reads and writes and the application routes to it, replication is healthy again (Premium: link provisioning status Succeeded with the roles back as planned; active form: the instance is a member of the group, or was recreated into it, and Geo Replication Healthy is healthy), the canary key has the same value in every region and the data written during the drill is present on the primary.
- How to measure: the drill that follows TC-3 runs the Failback table and checks the link or group state, the metrics and the canary and sample keys on both sides.
- Evidence: the drill record with the failback timestamps, the link or group state output and the key comparison.
- Frequency: every DR drill

### TC-5: The region-outage steps work, and the outage itself is a design check
- Applies to: geo-replication
- Pass condition: two parts. Measured: on a rehearsal pair or group of the same product and tier with no production data, the region-outage steps run to the end: for Premium the unlink leaves the former secondary accepting reads and writes with the synced data and the link can be rebuilt; for the active form the force unlink removes a member, the others keep accepting writes, and the removed instance can be deleted and recreated into the group; the time of each step is recorded. Design check, not drillable: a real regional outage cannot be triggered, so the detection of the outage (Service Health and the application's health check), the memory headroom of the surviving instances for the metadata of a down member, and the runbook's decision point for the unlink or force unlink are checked by review; it passes when each alert exists and fires on a test, the runbook names who decides and on which signal, and the memory alert threshold is set below the point where the instances could run out of memory.
- How to measure: the rehearsal run with timestamps and the group or link state after each step; a review of alerts, runbook and application health check with an alert test.
- Evidence: the rehearsal record, the review record with its date and the alert test records.
- Frequency: the rehearsal every DR drill; the design check after every change to the alerts, the runbook or the application's health check

### TC-6: The DR workload can connect and authenticate to the DR cache
- Applies to: geo-replication, rebuild-in-dr
- Pass condition: from every DR network that runs consumers, the DR workload's identity connects to each DR cache over TLS through its private endpoint, authenticates with a Microsoft Entra token (or the key of that cache where Microsoft Entra is not used) and runs a write and a read of a test key; the client refreshes its token before it expires; no connection string, key or token is held in code; where keys are used, the DR configuration holds the key of the DR cache and not the primary's.
- How to measure: for Azure Managed Redis the Azure CLI connectivity test (the redisenterprise test-connection command that Learn describes) or a ping from the DR network; for the others a probe in the DR network that authenticates as the workload and writes and reads a test key; a review of the application's configuration for secrets.
- Evidence: the probe log with the identity, endpoint, time and result, and the review record.
- Frequency: weekly, and after every change to the identity, the keys, the network or the cache

### TC-7: The newest export is fresh, readable and importable in the DR region
- Applies to: rebuild-in-dr
- Pass condition: for a cache that supports export (not Basic or Standard), the newest export file in the DR storage account is no older than the export interval the team sets (the Estimated RPO parameter), is a blob of a type the DR cache imports, is of a Redis version no newer than the DR cache's, and imports into the DR cache (or a test cache of the same tier and region) with the canary keys present and the key count within the team's tolerance of the primary's at the time of the export.
- How to measure: list the blobs of the DR storage account with their time stamps; read the Redis version of the file and of the cache; for the restore test import the file into the standby or a test cache and compare canary keys and key count (the import deletes existing data and makes the cache unavailable, so it never runs on a cache that serves traffic).
- Evidence: the blob listing, the freshness report with the age and its limit, and the import record with the canary and key count comparison.
- Frequency: freshness daily, restore test monthly

### TC-8: The application starts from the DR cache within the Estimated RTO and the source of truth holds the load
- Applies to: rebuild-in-dr
- Pass condition: in a drill, the time from the declaration to the first request served through the DR cache is within the switch-over time the team sets for the Estimated RTO (creating or readying the cache, the import if used, and the switch), the application works with an empty or partially loaded cache (cache-aside with fallback to the source of truth), and the source of truth stays within the capacity recorded in Build while the cache warms up.
- How to measure: a drill that runs the Failover steps for rebuild-in-dr with a test deployment of the application, timing each step and recording the request rate and latency of the source of truth during the warm-up.
- Evidence: the drill record with timestamps, the measured time, the application log and the load graph of the source of truth.
- Frequency: every DR drill, and after every change to the cache template or to how the application uses the cache
